## Booking and availability decisions

Availability is set **once** in the existing `availability` collection and shared by every lesson, coaching session, intro and Build with Shaun consultation. `listAvailabilityRows` and `listBusy` remain global: a booking of any type blocks the same calendar. There are no per-lesson or consultation-specific windows.

The existing `globals.booking_slot_step_mins = 30` remains unchanged. A 15-minute intro starts at `:00` or `:30` and occupies exactly 15 minutes, plus any existing global padding. A consultation occupies 30 minutes. Both obey the existing notice, horizon, hold expiry and cancellation cutoff settings.

The limit is **one live free booking per user per zero-priced lesson type**. Live means an unexpired `held` booking or a `confirmed` booking with a future `start_at`. An intro and a consultation can be held/booked concurrently at different times; two live intros or two live consultations cannot. Existing total live-hold cap (four), OTP/session, ownership and overlap checks still apply. Released/expired holds and cancelled/completed/no-show/past bookings do not consume the free allowance.

## Checkout and cancellation

The server resolves every line using the existing catalogue/hold checks. Only an all-zero cart bypasses Square; any positive-priced line keeps the existing Square payment-link/webhook path. Orders retain `pending` → `paid`, existing `paid_at` and zero monetary totals; `payment_provider`, `payment_session_id`, and `payment_intent_id` stay **null**. No new schema field or enum value is required by the repository's nullable order types or the schema record. `markFreeOrderPaid` and Square's `markOrderPaid` share the same idempotent paid transition, then call `fulfillPaidOrder`. Bookings become `confirmed`, not abandoned as expiring holds.

Because no Square webhook retries a free order, retrying the exact owned free booking cart resumes its existing pending/paid order and fulfilment. It cannot adopt a paid, mixed, foreign, cancelled or refunded order. Shared fulfilment still flags `needs_attention` if a slot was lost or a newer order owns the booking. The confirmation page uses actual booking status before claiming confirmation and displays attention separately.

Cancellation reads the **original order item's unit price**, not the current catalogue price or the mixed order total: zero-priced booking lines never create refund credits, even after repricing, rescheduling, or inclusion in a paid cart. Paid lines keep their refund credit even if their catalogue lesson later becomes free. Credit-source bookings retain their existing release semantics. Legacy purchase bookings without an order line use the lesson price as a conservative fallback; missing price data must not mint a free credit. There is no automatic monetary refund on these free orders.

The repo enforces limits on hold, credit booking, reschedule and expired-hold recovery. It checks before inserting and recounts afterwards, cancelling a competing booking, matching the existing credit-overspend approach. This is application enforcement, not a database uniqueness constraint: direct admin/API inserts bypass it, transient races can create rows before rollback, and a failed cancellation/read needs operator attention. The existing SQL guard enforces time overlap only. No new production DDL was applied.
